# 待办工作分工与协作计划

> 面向：项目负责人（业务/验收）与新入职开发员工（代码实现）
> 更新日期：2026-08-25
> 用途：把当前项目**尚未完成**的工作明确分为「需要业务决策/验收」与「工程实现」两类，界定双方职责，避免重复与遗漏。

## 1. 背景与分工原则

项目已完成任务化改造主体（PR #10 合入 main：采集任务、AI 要求规范化、质检框架 v2 任务符合度、按任务定价结算、任务大厅与任务管理页），并已建立生产基线（PR #11）与国内镜像源修复（PR #12），本地与服务器（114.55.6.224 `/srv/evdp`）均对齐到 `16368347`。

后续开发由两人协作推进，分工原则：

| 角色 | 负责什么 | 不负责什么 |
|---|---|---|
| **项目负责人（你）** | 业务规则定夺、验收标准、标注/合规数据提供、架构方向、最终验收 | 不写业务代码；不逐行 review 细节实现 |
| **新员工（开发）** | 按本计划与负责人确认的规格实现功能、测试、文档、运维自动化 | 不擅自变更业务口径/评分规则/定价逻辑；重大设计先确认 |

协作基线：
- 代码统一走 **GitHub**（分支 → PR → review → 合入 `main`），本地仓库为唯一真源，服务器由负责人或 CI 部署。
- 每个任务完成需满足 **DoD（Definition of Done）**：代码 + 测试 + 文档 + 本地可运行 + 服务器可部署验证。
- 涉及**业务口径**（评分权重、阈值、定价、安全策略、禁采清单）的改动，必须先由负责人书面确认再实现。

## 4. Part A：负责人职责（决策、数据、验收）

> 这些工作**无法由开发独立完成**，需要你的业务判断、数据或验收口径。完成后把结论写进对应 issue/文档，再派给开发执行。

### A1 五维评分阈值/系数人工校准【高】
- **内容**：当前构图/手部/清晰度等判定阈值与系数基于经验值，需用 500~1000 条**人工标注集**校准。
- **你的职责**：提供标注数据集与标注标准（或确认由开发按你给的规范做标注工具与采集流程）；确认校准后的目标指标（通过率、误判率上限）。
- **验收口径**：给出「达标才算合格」的量化指标（如质检通过率分布、人工复核一致率）。

### A2 D4 任务符合度权重与硬性否决策略【高】
- **内容**：当前默认「符合度比例 × 场景匹配因子，hard 未满足进人工复核」；上线后需按实际质检分布确认是否调整权重、是否把「hard 未满足」从复核升级为直接否决、compliance_ratio 复核阈值取多少。
- **你的职责**：观察 1~2 周线上数据后给出结论；在此之前维持现状。
- **输出**：一条明确的规则（权重值 + 否决条件 + 复核阈值），供 B1 做成可配置。

### A3 结算口径统一【中】
- **内容**：现在「分档系数」与「通过阈值（passThreshold）」两处口径并存，存在边界不一致。
- **你的职责**：决定统一策略（例如：低于阈值一律 0 分且不进档；或去掉独立阈值只按分档）。
- **输出**：书面口径 → 开发实现并回归结算测试。

### A4 目标库存模式定义【中】
- **内容**：第五维目前只有「实时存量快照 + 冷启动」，缺少目标库存（目标时长/存量目标与系数曲线）。
- **你的职责**：明确目标库存的业务含义（如每个场景/动作想收到多少条、达到目标后系数如何衰减）。
- **输出**：目标库存参数表 → 开发实现。

### A5 隐私/安全禁采清单【高】
- **内容**：AI 质检的隐私/安全否决依赖提示词里的通用表述，缺业务侧明确禁采清单。
- **你的职责**：给出禁采内容清单（人脸/门牌/车牌/屏幕账号/定位等，以及行业/场景特例）。
- **输出**：清单文档 → 开发接入提示词与校验规则。

### A6 生产账号安全策略【高】
- **内容**：生产账号当前密码策略依赖人工管理；服务器 `/root/evdp-initial-credentials.txt` 已过期。
- **你的职责**：决定是否启用「首次登录强制改密」、密码复杂度/轮换周期；确认清理过期凭据文件。
- **输出**：策略 → 开发实现（B 侧可在你确认后先清理凭据文件）。

### A7 提交数量上限/频率限制规则【中】
- **内容**：当前单人对任务提交无上限，依赖质检否决与近似重复兜底。
- **你的职责**：决定是否需要限制（每人每任务上限？每日上限？是否按任务类型区分）。
- **输出**：规则 → 开发实现（B9）。

## 5. Part B：新员工职责（工程实现）

> 这些有明确技术规格，可独立交付。**标 ⭐ 的为高优先级**。实现前如需业务参数（A 类结论），按「依赖」列等待确认或使用当前默认值先行实现（可配置化）。

### B1 D4 权重/否决阈值可配置化【高 · 依赖 A2】
- 把 D4 权重、场景匹配因子、hard 未满足否决/复核开关、compliance_ratio 复核阈值从硬编码改为可配置（建议放入质量规则版本化体系），管理界面可发布。
- 验收：改配置不影响历史结果（快照锁定）；前后端 + 测试。

### B2 ⭐ 近似重复升级：视觉指纹 / 向量检索（Qdrant）【高】
- 现状：近似重复基于元数据相似度（时长/大小/分辨率/帧率）；README 已标注升级方向。
- 任务：接入 Qdrant（本地 compose 已有该服务），对视频抽帧生成视觉指纹，近似重复判定加入视觉相似度；评估成本与召回率。
- 验收：重复/近似重复检出样例集上对比新旧方案。

### B3 C_unique 接入向量库【中 · 依赖 B2】
- 第五维 `C_unique` 目前主要靠 SHA-256 完全重复 + 元数据近似重复；接入向量库后按视觉相似度输出权威 `C_unique` 系数。

### B4 积分周期定时自动锁定【中】
- 增加调度器（如每日/每周按业务日期自动锁定），保留管理员手动锁定与审计；需与负责人确认自动锁定边界（避免误锁未复核数据）。

### B5 团队单价版本管理与价格审计【中】

### B6 管理员按任务结算汇总视图【中】

### B7 团长端按任务筛选/聚合【低】

## 7. 协作与验收建议

1. **派活方式**：每个任务开一个 GitHub issue（引用本文件编号），PR 关联 issue；负责人只验收 PR 合入 `main` 后的可运行状态。
2. **DoD**：代码 + 测试（`pnpm test/typecheck/build` 全绿）+ 文档更新（用户手册/开发文档）+ 本地可运行 + 服务器可部署验证（涉及 A 类决策的附确认记录）。
3. **口径冻结**：涉及评分权重、阈值、定价、安全策略、禁采清单的改动，PR 描述须注明「已获负责人确认（issue #xx / 日期）」。
4. **环境**：开发用本地 docker（`compose.yaml`）+ 本地 web dev；部署验证用生产服务器（`compose.prod.yaml`），避免开发直接改生产 `.env`。
5. **文档维护**：每次合入后同步更新 `docs/用户使用手册.md` 与 `docs/开发人员功能文档.md`，保持本文件编号与实现状态一致（已完成项移入 §2 基线）。
